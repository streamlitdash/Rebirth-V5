# V8 — one complete implementation guide

This branch contains the **working application changes**, not just instructions. This is the only Markdown guide on `v8`. It replaces the separate Hero, JTD, Quick Risk and refresh-interaction instructions for these features. Other GitHub branches are unchanged.

The screen should work like this:

1. Start or refresh the app: the familiar hero shows the work, waits for the visible results, then disappears.
2. Click a JTD underlying or group: its table opens. Filter within the table, change page, and read the total at the top.
3. Open Quick Risk: search once, select an identity and arrange the pivot. The appropriate chart appears automatically at full width.
4. Open Data: search once, then choose Risk, Market or Both. Switching mode keeps the selection.
5. Open an underlying from Risk Explorer or Quick Risk/Market in Data: the underlying is carried across. Risk page filters are carried with a Risk handoff.
6. Open Stock: see Stock and dStock in an expandable hierarchy, click CRDS/CIDS for history, and open Raw connector data only when needed.
7. Return to Risk: keep the existing table and expansion. Rebuild once only if a newer data revision arrived while you were away.
8. Open Statics Write: the dataframe picker uses the full available width above its action buttons.

## 1. Install the coherent version first

### 1.1 Choose the straightforward route

If you want the complete version, use the code from the **v8 branch**. You do not need to apply the old Markdown instructions again.

1. Save your current application in a separate folder or Git commit.
2. Open this repository on GitHub and choose branch **v8**.
3. Download that branch or check it out into a separate working folder.
4. Keep your production connector implementations, connection settings, data, saved views and archive. Those are your environment-specific inputs. This repository still includes demonstration sources; downloading the branch does not connect it to your production systems.
5. If your connectors live inside an application file being replaced, first save that connector code. Move the connector implementation into the corresponding v8 source boundary with the same arguments and return columns. Do not overwrite it with the demonstration function.
6. Install the dependencies from `requirements.txt` in your Python environment. Use the same tested versions while applying this change.
7. From the folder containing `app.py`, run:

```sh
python -m pip install -r requirements.txt
python app.py
```

8. Reload the browser fully so that it receives the new Python callback graph and JavaScript together.
9. Run the checks in chapter 10 before using this version for your normal workflow.

### 1.2 If you are copying changes into your current installation

The chapters below give the implementation order. **Copy the complete v8 versions of the named files**, rather than pasting a second definition below an old function. A replacement means replace the old contents at exactly that path. An addition means create the file at that path.

Full-file replacement applies to the repository version. Get all the files from the same `v8` version. Finish chapters 2–9 before restarting: some files depend on the Stores and callbacks introduced by another chapter. Where a file appears in two chapters, copy it once; the file already contains both changes.

The complete file checklist is in chapter 11. It also includes the earlier supporting changes now present as actual code. If you already implemented those changes, keep the v8 version as the reference and reconcile your connector customisations.

## 2. Keep the hero familiar and make completion reliable

### 2.1 What was wrong

There are three different moments in a refresh:

1. The backend obtains and calculates the data.
2. The refresh callback finishes preparing its result and returns to the browser.
3. The visible tables and charts finish rendering that result.

A backend progress message alone cannot confirm all three. Equally, replacing the hero's HTML does not mean the refresh stopped. Earlier combinations of instructions mixed these events, which could produce disappearing heroes, stale waiting messages or an apparent instant completion.

V8 uses one browser request ID, one explicit callback result and small completion messages from the visible renderers. A completion message contains an ID, revision and status; it does not contain another copy of the risk data.

### 2.2 Apply the files in this order

1. **Add** [`cube/ui/s08_refresh_views.py`](cube/ui/s08_refresh_views.py). Its `refresh_view()` helper adds a completion message to the callback that already renders a result. It preserves errors and the last good display.

3. **Replace** [`cube/app/s05_progress.py`](cube/app/s05_progress.py). `progress_payload()` reports whether the startup worker is still alive. A success label does not release the hero while that worker still runs.
4. **Replace** [`cube/pages/risk/s15_refresh.py`](cube/pages/risk/s15_refresh.py). Its clientside dispatcher creates the request before calling Python. `refresh_pipeline()` receives that request and returns an explicit outcome on every exit: complete, failed, rejected, busy or no work. There is one dispatcher and one server refresh callback.
5. **Replace** [`cube/app/s07_factory.py`](cube/app/s07_factory.py). Keep one shared refresh shell and the independent revision publisher. The publisher must release the new revision before waiting for callbacks that need that revision; reversing that order causes a wait that cannot finish.
6. **Add** [`assets/refresh_views.js`](assets/refresh_views.js). It follows the visible results and checks that the new HTML and Plotly graphs have mounted.
7. **Replace** [`assets/s12_refresh.js`](assets/s12_refresh.js) in full. Do not append the older restore-panel or waiting-server snippets. This file owns the lifecycle and repaints a replacement hero from the retained state.
8. Use the coordinated renderer files: `cube/pages/risk/s07_explorer.py`, `s14_workspacecallbacks.py`, `cube/pages/pnl/s05_sendcallbacks.py` and `s08_aggregate.py`. They include their existing outputs plus the small renderer completion output. The final State supplied to each decorated callback is the current refresh request.
9. Use v8's `assets/s13_risk.js`. It retains normal delegated clicks and Shift+F9. Warm refresh dispatch is owned by the clientside callback, so do not add a second native click handler that starts another hero or another refresh.
10. **Replace** `cube/pages/stock/s04_callbacks.py` and apply the coordinated Data files in chapter 5. Their visible results also acknowledge refresh completion. Data acknowledges after its player has supplied the new graphs. Statics is not rebuilt by a financial refresh and does not add unrelated work to the wait.

### 2.3 Appearance and timing

The original hero HTML and styling are retained. Titles use the familiar operation names, such as **Refreshing P&L**, **Reloading all risk** and **Loading Cube data**. There is no extra global loading overlay above it.

While connectors run, their live progress updates appear. Once the callback returns successfully, the hero says **Updating tables and charts**. It clears the stale connector name, product counter and source. The final stage remains active until the required visible results finish. A fast stage missed between progress samples is not falsely labelled as an observed completed call.

After successful completion, the hero hides after 300 milliseconds, matching the earlier behaviour. A warm failure remains visible for five seconds and the error remains available in the normal error display/log. A cold-start failure stays visible with Retry. An unconfirmed connection/process interruption is not silently converted into success by a timer.

An old hide timer cannot hide a newer refresh. A remounted hero cannot reset the request or resurrect an already hidden completion panel.

The hero belongs to startup or the refresh initiated in this browser. Another browser's warm refresh can update the committed data here, but does not create a local hero waiting for a callback receipt it can never receive.

Normal empty refresh-request Stores during page loading now do nothing; they are not reported as invalid user requests. Actual malformed requests still receive a clear rejection. Keep the updated `s15_refresh.py` guard and the shared receipt helper when applying the Stock changes.

### 2.4 Keep the app usable during refresh

Keep the last committed snapshot readable. The existing writer controls can be disabled while a writer is running; navigation, table expansion and searching should remain available.

In `s07_explorer.py`, the filter-options callback observes `clear-cache-complete-store.modified_timestamp`, not the data output of the long refresh callback. This removes the dependency that previously queued ordinary filter interactions behind the refresh.

Do not wrap the entire page in `dcc.Loading`, add a full-screen pointer-blocking layer, or disable all inputs to keep the hero visible. Its visibility is controlled by the lifecycle, independently of page interaction.

## 3. Simplify JTD

### 3.1 The intended table

There is **no separate search bar**. Type beneath the relevant column header, as you do in Statics. There are 25 detail rows per page and a **Total (filtered rows)** row at the top of every page.

The default order is absolute Risk JTD, largest first. Thus `-1,000` appears before `+500`. Header sorting can override this; clearing it restores the default.

Negative measures are red; zero and positive measures are black. Values have commas and two decimal places. CRDS stays text, including leading zeros.

The DataTable uses `filter_action="custom"` and server paging. “Custom” here means the server filters the whole result behind the ordinary filter row; it does not mean another visible search interface. Only the page plus its total is sent to the browser.

### 3.3 Use it and check the result

1. Choose JTD in the Credit view and click the underlying name.
2. A click on `therm` includes the surviving raw underlying rows for that selection. A Group click includes its children. TOTAL includes the entire current branch. Promoted names and Cross/Single, Credit Multi and SplitVA follow the same validated selection path.

4. Change to page 2. The total must stay the same.

The total covers **all matching rows across all pages**, not just the visible 25. Missing numeric values remain missing. The existing underlying-based reference table does not invent Portfolio or Activity allocations if the JTD source does not provide those fields.

### 3.4 Why the published JTD table was empty

The repository's bundled `data/s13_jtd.csv` contains only the header `Underlying` and **zero data rows**. A working callback cannot produce CRDS, EAD or JTD positions from that file. The main risk aggregates do not contain the missing trade-level reference records.

The updated table remains visible and explains the missing source. The ordinary Underlying, CRDS, Risk JTD and EAD filter boxes remain available. No rows or financial values are invented.

To supply your source:

1. Keep your populated `data/s13_jtd.csv` when copying the branch. Alternatively, set the server environment variable `CUBE_JTD_REFERENCE_PATH` to your populated CSV path.
2. A relative path resolves from the folder containing `app.py`. On Plotly Cloud, bundle that populated file with the app or provide an existing mounted path; a path on your laptop is not available to Cloud.
3. Keep the exact raw `Underlying` values used by risk. Keep `CRDS` text and numeric `Risk JTD` / `EAD`.
4. Restart after changing the environment setting. Click an underlying or parent Group again.
5. An empty selected branch is different from an empty whole file; the displayed message distinguishes these cases.

Local browser checks cover Single, Multi and Split VA using populated fixture data and the actual empty bundled file. Authenticated Cloud screen checks were not available in this session.

### 3.5 Add another numeric JTD measure

Add its column to your source and add its exact name to `JTD_NUMERIC_COLUMNS` in `cube/services/s08_jtd.py`. That gives it numeric filtering, formatting and totals. Include only additive measures. Do not total identifiers, rates, percentages or tenor ranks merely because they look numeric.

## 4. Make Quick Risk simple and fast

### 4.1 The screen

1. Open Quick Risk.
2. Search for an underlying, type or Greek in its existing dropdown.
3. Select a result. Typing alone does not select the first result or build a financial pivot.
4. Arrange the pivot using the existing field picker.
5. Read the automatic chart and pivot. There is no chart-type selector.

| Data shape | Automatic Quick Risk chart |
| --- | --- |
| Spot, with no tenor | No chart; the pivot still shows the values |
| Swap tenor | Full-width Total Risk bars with XVA and Hedge lines |
| Option tenor only | The same bars and lines on the option-tenor axis |
| Swap and option tenor | Full-width heatmap |

The tenor chart shows **Total Risk as bars on the left axis** and **Risk XVA and Risk Hedges as lines on the right axis**. Each axis has its own scale, with equal positive and negative limits, so both zero lines meet at the vertical centre. The heatmap shows **Total Risk**. It uses the financial aggregation and tenor order used by the existing detail views, with its own uncluttered full-width layout. It does not embed the narrow tenor-selector panel.

If an identity has genuinely mixed shapes, each tenor-shaped part gets the matching plot; spot positions remain in the pivot. Missing surface cells stay missing. They are not turned into zero risk.

### 4.2 Why the search is faster

Previously, even an optimised Python search still needed a server round trip for each keystroke. Those requests could wait behind other work.

V8 sends a compact **list of names** when the workspace opens, the committed revision changes or the relevant filters change. The browser searches that list locally. It displays at most 100 matching choices and retains a valid selection. This is a limit on the visible suggestions, not on accessible underlyings or financial rows.

There is one replaceable label index per Quick control. It does not accumulate search-query caches, complete DataFrames or table versions. A selected pivot still uses the full selected data.

The existing pivot display shows at most 250 leaf groups and reports the displayed count; its totals still use the full selection. A heatmap above 250,000 cells asks for narrower shared filters before allocating its plotting grid. Neither display limit deletes positions.

## 7. Include the live market point without inventing history

The data flow is:

`connector → validated committed snapshot → selected history read → archived rows plus current rows → Data chart`

1. Your current market connector supplies the current quote using its existing product schema.
2. The manager validates and commits it. The committed **Market Date** is its date.
3. Data reads the selected archived identity and the matching committed current rows.
4. For a normal live snapshot dated today, today's value appears as the newest daily point. If that same date already exists in the archive, the current committed rows replace that date in the displayed query; they are not added twice.
5. If you deliberately forced a historical Market Date, the point keeps that historical date. The app must not relabel an old quote as today's live quote.
6. Risk keeps its own Risk Date. It is not moved to today's date merely to line up with a newer market point.

This is a daily view: several intraday refreshes update the current day's point rather than manufacture multiple daily observations. The archive on disk is not overwritten by viewing Data. A historical point remains available after restart only if your existing archive process has persisted it. This UI change does not create missing P&L, Stock or risk history for dates you have never stored.

When current Risk rows establish a source/day but none survive the selected Portfolio filter, an old archived value for that same source/day must not reappear. V8 removes the replaced archive rows before applying the filter. If an entire identity has disappeared and no current row or explicit removal-date record exists, the app can show its stored history but cannot invent a dated zero position.

Size checks protect the selected browser history, not the total amount of data you may keep on disk. A grid with 100 dates × 100 swap tenors × 100 option tenors would contain one million cells even though Play shows only one date at a time. The grid size is checked before allocation. Narrow the period or identity when asked; do not remove the check and build the grid first.

The existing Data query limits are **10,000 raw rows** and **16,000 canonical date/tenor cells** per selected query. They are not a 10,000-row limit on the main risk snapshot. A large underlying's long history may need a shorter period or narrower Risk filters. V8 keeps these limits; it does not silently omit rows to fit them.

## 8. Replace the complicated Stock workflow


### 8.4 Promotion and adding columns

1. The default threshold is `STOCK_PROMOTION_THRESHOLD = 20_000` in `s01_data.py`.
2. Sum dStock for each **sign-off group + CRDS/CIDS**, across its Groups. Promote when the absolute result is **strictly greater than** 20,000.
3. A +30,000 and -28,000 position for the same identifier/sign-off group net to +2,000 and stay in Other. A -25,000 change is promoted. Exactly ±20,000 stays in Other.
4. Sign-off group stays highest. Promoted identifiers appear immediately underneath, ordered by absolute change. They are excluded from Other, so nothing is counted twice.
5. Initial expansion shows the sign-off groups' promoted identifiers and Other. Clicking Other opens Group, then Counterparty name, then CRDS/CIDS. Clicking a promoted identifier both expands it and opens history.
6. To add an index column, return it from your connector. It appears automatically after the default hierarchy and in the raw table. No whitelist, schema validator or extra table callback must be edited.
7. To change the leading dimension names/order, edit `STOCK_INDEX_ALIASES` in `s01_data.py`. Existing aliases include `SignoffGroup`, `CPTY`, `CRDS` and `CIDS`. Source names remain unchanged. CIDS is used if present; otherwise CRDS.
8. Only Stock and dStock are summed in the hierarchy. Additional numeric columns remain dimensions there; the flat raw table formats numeric columns with commas and red negatives.

The raw table reads 25 rows at a time after filtering/sorting the complete source frame on the server. Each column has its own ordinary filter box. Opening branches or paging raw data does not call your current connector again.
